# SELTE

Мобильное приложение — социальная сеть для стилистов и моды с функционалом ИИ-гардероба.

## Исходное ТЗ (как задано при создании проекта)

> Социальная сеть для стилистов и моде с функционалом гардероба
>
> Мы спроектировали мобильное приложение на стыке Fashion-соцсети и умного
> ИИ-гардероба. Это экосистема, которая связывает обычных пользователей,
> персональных стилистов и нейросети для составления образов.
>
> **Суть и ключевой функционал:**
>
> - **Социальная лента (Discover & Lookbooks):** стритстайл и лукбуки от
>   стилистов и инфлюенсеров. На фото есть интерактивные метки (pin) на
>   одежду: кликнув по вещи или брюкам, можно узнать бренд, состав и похожие
>   вещи.
> - **ИИ-Гардероб (AI Digital Hub):** пользователь сканирует свои вещи (или
>   селфи в полный рост), ИИ сегментирует одежду, удаляет фон и раскладывает
>   всё по виртуальным «полкам» (Bento-сетка: верхи, низы, обувь,
>   аксессуары).
> - **Связка с реальными стилистами:** профили мастеров с портфолио и
>   тарифами. Пользователь может в один клик расшарить доступ к своему
>   виртуальному гардеробу стилисту, чтобы тот собрал капсулу.
> - **ИИ-стилизация:** кнопка генерации луков («Собрать образ из моего
>   гардероба в стиле [Имя Стилиста]») с учётом погоды за окном.
> - **Нативный seamless-флоу:** полноценный путь входа (Splash → Ввод Email
>   → 4-значный OTP-код) с переходом на главный экран и плавающей нижней
>   навигацией.
>
> **Дизайн-система:**
>
> - Стиль: Calm Interface и микро-ньюморфизм (мягкие объёмные тени,
>   тактильный UI).
> - Палитра: тёплые нейтральные тона (Sand, Warm Cream, Deep Charcoal,
>   Muted Terracotta).
> - Стек: React / React Native (Tailwind CSS) + Django REST Framework для
>   бэкенда.

Полный технический план (архитектура, доменная модель, API, ИИ-пайплайн,
roadmap) — в [`docs/architecture/fashion-app-technical-plan.md`](docs/architecture/fashion-app-technical-plan.md).

## Текущее состояние репозитория

Стартовали с generic Django+React шаблона (Turborepo). React Native
мобильного клиента (`apps/mobile`) пока нет — заведён только бэкенд.

Что уже сделано в `apps/api`:

- **Кастомный `User`** (`accounts.User`) — вход по email, без пароля у
  обычных пользователей (`AUTH_USER_MODEL = "accounts.User"`, выставлено до
  первого `migrate`, менять после этого нельзя без пересоздания БД).
- **OTP-флоу** (`accounts/`): `POST /api/auth/otp/request/` → 4-значный код
  кладётся в Redis (TTL 5 мин, cooldown повторной отправки 60 сек, лимит 5
  попыток / блокировка 15 мин) и уходит письмом через Celery-таску;
  `POST /api/auth/otp/verify/` → создаёт пользователя при первом входе и
  возвращает JWT (`djangorestframework-simplejwt`); `POST
  /api/auth/token/refresh/` — обновление access-токена.
- **Redis** — общий для кэша Django (`django-redis`, БД `1`) и брокера
  Celery (БД `0`).
- **Celery worker** — отдельный сервис в `docker-compose.yml`, команда
  `celery -A core worker -l info`, письма пока уходят в консольный
  email-бэкенд (см. логи `docker compose logs -f worker`).
- **Swagger/OpenAPI** — `drf-spectacular`: `GET /api/docs/` (Swagger UI),
  `/api/redoc/`, `/api/schema/`.

Мобильный флоу входа ложится на эти ручки как: Splash → «Начать» → экран
email (`otp/request`) → экран кода (`otp/verify`) → главный экран.

## Известные грабли

- `docker-compose.yml` пробрасывает Postgres на хостовый порт `5433` — если
  TablePlus/psql не могут подключиться с ошибкой `role "postgres" does not
  exist`, в первую очередь проверить, не занят ли `127.0.0.1:5433` каким-то
  другим процессом (например, забытым `kubectl port-forward`):
  `lsof -nP -iTCP:5433 -sTCP:LISTEN`.
- `.env` → `DJANGO_SECRET_KEY` содержит `$wve` — Docker Compose трактует
  это как подстановку переменной и обнуляет кусок значения. Сейчас
  безвредно, т.к. `docker-compose.yml` не прокидывает эту переменную в
  контейнер `api` (используется дефолтный dev-ключ из `settings.py`). Если
  будете прокидывать реальный секрет — экранировать `$` как `$$` или
  сгенерировать ключ без `$`.
