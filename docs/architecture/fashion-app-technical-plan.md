# SELTE — технический план и архитектура
### Fashion-соцсеть + ИИ-гардероб

*Дата: 26.08.2026*

---

## 1. Обзор и допущения

Продукт связывает три роли: обычный пользователь, персональный стилист и нейросеть-ассистент. Ядро — ИИ-гардероб (оцифровка личных вещей) плюс соцсеть лукбуков с интерактивными метками на одежде.

Текущий репозиторий (`SELTE`) — это generic-шаблон Turborepo:

| Компонент | Статус в репо |
|---|---|
| `apps/api` — Django 5.1 + DRF | ✅ рабочий скелет (health-check, tasks-app) |
| `apps/web` — React 19 + Vite | ✅ рабочий скелет, назначение под продукт не определено |
| `apps/admin` | 🗂️ пустая заготовка |
| `apps/space` | 🗂️ пустая заготовка |
| `packages/shared-ui / types / utils` | 🗂️ пустые заготовки |
| React Native / мобильный клиент | ❌ отсутствует, нужно добавить |
| Postgres, Docker Compose | ✅ настроены |

**Допущения** (не были заданы явно в брифе, фиксирую здесь, чтобы дальше не расходиться):
- Основная платформа — мобильный клиент (React Native); `apps/web` со временем становится либо лендингом, либо веб-версией «на потом», `apps/admin` — внутренняя панель модерации/каталога.
- MVP ориентирован на один регион/язык, авторизация только по email+OTP (без телефона).
- Оплата тарифов стилиста в MVP не обязательна (см. открытые вопросы, п. 10).
- Команда небольшая (судя по масштабу шаблона) — решения ниже оптимизированы под скорость запуска, а не под пиковый масштаб соцсети с первого дня.

## 2. Функциональные требования (из брифа)

1. **Лента (Discover & Lookbooks)** — стритстайл/лукбуки стилистов и инфлюенсеров; интерактивные pin-метки на одежде на фото → бренд, состав, похожие вещи.
2. **ИИ-гардероб (AI Digital Hub)** — сканирование вещей/селфи в полный рост → сегментация, удаление фона, раскладка по «полкам» (Bento-сетка: верх/низ/обувь/аксессуары).
3. **Связка со стилистами** — профили с портфолио и тарифами; шаринг гардероба стилисту в один клик для сборки капсулы.
4. **ИИ-стилизация** — генерация образа «в стиле [Стилист]» с учётом погоды.
5. **Onboarding-флоу** — Splash → Email → 4-значный OTP → главный экран, плавающая нижняя навигация.

## 3. Нефункциональные требования

- **Медиатяжёлый продукт**: оригиналы фото, обработанные cutout-изображения, лента с картинками стилистов → нужны объектное хранилище + CDN с первого дня, иначе диск/бэкап Postgres-инстанса быстро упрётся в лимиты.
- **Асинхронный ИИ**: сегментация и генерация образов — не user-facing синхронные вызовы (секунды-десятки секунд) → очередь задач + polling/push статуса на клиенте.
- **Приватность гардероба**: доступ стилисту — не «всё или ничего», это отдельная модель прав с отзывом.
- **Стоимость инференса**: сегментация + LLM-генерация на пользователя — стоимость растёт линейно с DAU, нужен слой кэширования и квоты.
- **Постепенный рост ленты**: на старте — простой pull/pagination, без преждевременного fan-out/realtime.

## 5. Доменная модель (ключевые сущности)

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| `User` | аккаунт | email, роль (`user`/`stylist`/`admin`), профиль |
| `StylistProfile` | карточка мастера | портфолио (галерея), тарифы, специализация/теги стиля |
| `WardrobeItem` | вещь в гардеробе | photo_raw, cutout_url, категория/подкатегория, цвет, бренд (опц.), источник (scan/purchase) |
| `WardrobeShare` | право доступа к гардеробу | user, stylist, scope (read-only), expires_at, revoked_at |
| `Post` / `Look` | лукбук в ленте | автор (стилист/инфлюенсер), изображение(я), подпись |
| `ItemPin` | pin-метка на фото поста | post, координаты (x%, y%), ссылка на `Product`/`Brand` или `WardrobeItem` |
| `Brand` / `Product` | каталог для «похожих вещей» | название, состав, ссылки на маркетплейсы |
| `OutfitCapsule` | собранный образ | список `WardrobeItem`, автор (AI/стилист), контекст погоды, стиль-тег |
| `StyleRequest` | запрос генерации образа | user, target_stylist (опц.), weather snapshot, статус, результат → `OutfitCapsule` |
| `Booking` | заказ у стилиста | стилист, пользователь, тариф, статус, (опц.) оплата |
| `Follow` / `Like` / `Comment` | соц-граф вокруг ленты | стандартные |

## 6. API-дизайн (DRF, ключевые группы эндпоинтов)

```
Auth
  POST /api/auth/otp/request        { email }
  POST /api/auth/otp/verify         { email, code } → access/refresh токены
  POST /api/auth/refresh

Feed
  GET  /api/feed?cursor=...
  GET  /api/looks/{id}
  GET  /api/looks/{id}/pins

Wardrobe (ИИ-гардероб)
  POST /api/wardrobe/scan           multipart photo → 202 + job_id
  GET  /api/wardrobe/jobs/{job_id}  → статус сегментации
  GET  /api/wardrobe/items?category=...
  PATCH/DELETE /api/wardrobe/items/{id}

Stylists
  GET  /api/stylists?tag=...
  GET  /api/stylists/{id}
  POST /api/stylists/{id}/share-wardrobe   { scope, expires_at }
  DELETE /api/stylists/{id}/share-wardrobe (отзыв доступа)
  POST /api/bookings

AI-стилизация
  POST /api/style/generate          { stylist_id?, mood? } → 202 + job_id
  GET  /api/style/generate/{job_id} → статус + OutfitCapsule при готовности

Каталог
  GET  /api/brands
  GET  /api/products/{id}/similar
```

Погода — не публичный эндпоинт: сервер сам обращается к внешнему Weather API по геолокации/городу пользователя в момент генерации образа, результат кладётся в `StyleRequest.weather_snapshot` (кэш на ~1 час на гео-ключ).

## 7. Асинхронный ИИ-пайплайн

**Сканирование вещи:** upload → Celery task → сегментация (удаление фона) → классификация (категория/цвет/тип) → cutout сохраняется в object storage → `WardrobeItem` обновляется → push-уведомление «вещь добавлена в гардероб».

**Выбор провайдера сегментации — trade-off:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Vendor API (remove.bg, Clarifai Fashion, облачный Vision) | Быстрый запуск, не нужна ML-инфраструктура/GPU | Cost per-request растёт с DAU, приватность фото пользователей у третьей стороны, меньше контроля над качеством для одежды |
| B. Self-hosted (U²-Net / cloth-segmentation модель, GPU-инстанс) | Ниже cost на масштабе, контроль над качеством и приватностью | Выше operational-сложность и time-to-market, нужен GPU и MLOps с первого дня |

**Рекомендация для MVP: вариант A**, но за интерфейсом `SegmentationProvider` (адаптер), чтобы замена на self-host не требовала переписывать пайплайн — только новую реализацию адаптера.

**Генерация образа («в стиле стилиста»):**
1. Rule-based предфильтр гардероба по погоде (температура/осадки → уместные категории).
2. LLM-вызов с промптом: сокращённые метаданные отфильтрованных вещей + теги фирменного стиля стилиста (из портфолио) + погода → модель возвращает `item_id[]` + обоснование.
3. Кэш результата по ключу `(user_id, weather_bucket, stylist_id, date)`, чтобы не дублировать дорогие вызовы в течение дня.

## 8. Инфраструктура (расширение текущего `docker-compose.yml`)

Уже есть: `api`, `web`, `db`. Добавить:

- **`redis`** — брокер для Celery + кэш ленты/погоды.
- **`worker`** — Celery worker (тот же образ `apps/api`, команда `celery -A core worker`) — оркестрация вызовов vendor API/LLM, классификация.
- **`beat`** *(опционально)* — периодические задачи (прогрев кэша погоды, дайджест-уведомления).
- **объектное хранилище** — MinIO локально, S3-совместимое в проде, для оригиналов и cutout-изображений + CDN перед ним.
- **ml-inference** *(если/когда self-host сегментации)* — отдельный сервис с GPU, за тем же адаптером `SegmentationProvider`.

## 9. Мобильное приложение (React Native)

Новый app в монорепо: **`apps/mobile`**. Рекомендация — **Expo** (managed workflow) для скорости старта; переход на bare RN — если понадобится глубокий кастомный доступ к камере/AR-примерке.

- **Навигация**: Splash → Auth stack (Email → OTP) → Main tab navigator (плавающий bottom tab): Discover / Wardrobe / Stylists / Profile.
- **Серверное состояние**: TanStack Query (React Query) — кэш ленты, гардероба, статусов job'ов (polling для async-задач).
- **Локальное UI-состояние**: Zustand/Context — например, состояние процесса сканирования вещи.
- **Дизайн-токены**: вынести в `packages/shared-ui` (или отдельный `packages/design-tokens`) — Tailwind-конфиг для **NativeWind**, чтобы Tailwind-классы работали в RN. Токены: `sand`, `warm-cream`, `charcoal`, `terracotta`.
- **Микро-ньюморфизм в RN**: нативный `box-shadow` там не работает как в вебе — реализуется через `react-native-shadow-2` либо комбинацию двух смещённых `View` (свет/тень) для тактильного эффекта.
- **Bento-сетка гардероба**: masonry/FlatList-grid компонент, группировка по «полкам» (верх/низ/обувь/аксессуары).
- **Pin-метки на фото ленты**: overlay `Touchable`-точки поверх `Image`, абсолютное позиционирование по `(x%, y%)` из `ItemPin`.

## 10. Открытые вопросы и риски

- **Права доступа к гардеробу**: бриф говорит «шарит в один клик», но не описывает объём/срок доступа стилиста — нужна явная модель (read-only, экспирация, отзыв, что стилист может делать с шаренным гардеробом).
- **Модерация UGC/брендов**: pin-метки указывают конкретные бренды — юридический риск (несогласованное упоминание бренда, неверный состав ткани) → нужен review-флоу для контента стилистов/инфлюенсеров.
- **Стоимость ИИ на масштабе**: сегментация + LLM-генерация — нужны квоты/rate-limit на бесплатном тарифе пользователя с первого дня, иначе unit-экономика не сходится при росте.
- **Realtime ленты**: в брифе не указано — предполагается pull-to-refresh/пагинация для MVP, без WebSocket.
- **Оплата тарифов стилиста**: провайдер не выбран; если целевой рынок — РФ, Stripe недоступен, стоит закладывать ЮKassa/CloudPayments вместо него.

## 11. Roadmap (MVP → V1 → V2)

- **MVP**: auth-флоу (email+OTP), гардероб (загрузка + сегментация через vendor API), лента с pin-метками (без верифицированных брендов, простые теги), профили стилистов (без бронирования/оплаты), rule-based капсула образа (без LLM).
- **V1**: бронирование стилиста + оплата, LLM-стилизация с учётом погоды, шаринг гардероба стилисту с моделью прав доступа.
- **V2**: собственная ML-модель сегментации (снижение cost на масштабе), каталог похожих товаров у брендов-партнёров, realtime-уведомления.

## 12. Что пересмотреть при росте

- Как только лента станет узким местом по чтениям — ввести fan-out/материализованную ленту вместо запроса по подпискам на лету.
- Как только объём сегментаций перерастёт по стоимости self-host GPU-инстанс — переключить `SegmentationProvider` на вариант B (см. п. 7).
- Как только появится второй регион/язык — вынести локализацию и, возможно, weather/payment-провайдеров за фиче-флаги по региону.
